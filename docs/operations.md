# 運用機能

[ドキュメント一覧](README.md) / [導入](install.md) / [サイト運用](sites.md)

導入を終えた管理者・公開担当者向けに、GitHub接続、公開確認、バックアップ、利用者の設定をまとめています。通常サイト（v1）の操作が中心です。専用ユーザー・CA状態を扱う場合は [隔離コンポーネント（v2）](pjas-cert.md) を参照してください。

| 機能 | 操作する場所 |
| --- | --- |
| 暗号化バックアップとデータ復元 | サイト → バックアップ・運用 → バックアップ |
| 障害・復旧のお知らせ | 接続設定と初回準備 → 通知方法 |
| エラー・アクセス・作業・常駐プログラム・定期処理のログ | サイト → バックアップ・運用 → ログを見る |
| 空き容量とサイト別の使用量 | サイト → バックアップ・運用 → 容量 |
| 公開するコードの差分確認 | 新しいバージョンを公開 → 変更点を確認する |
| Apache設定をGit履歴から復元 | サイト → バックアップ・運用 → 公開設定を戻す |
| 本番と分けた試験公開 | サイト → バックアップ・運用 → 試験公開 |
| 利用者ごとのサイト・操作権限 | 利用者とサイトの権限 |
| 認証アプリによる二段階認証 | ログインの保護 |
| 証明書の期限・公開アドレスの確認 | サイト → バックアップ・運用 → 証明書 |
| GitHubへのPushから自動公開 | サイト → バックアップ・運用 → 自動処理・予約 |
| 確認したコードの日時指定公開 | 公開前の確認 → 日時を指定して予約する |
| GitHub Appでprivateリポジトリを取得 | 接続設定 → GitHub App、サイト登録 → 接続方法 |

## 利用前の確認

新規サーバーは [導入手順](install.md)、導入済みサーバーは [更新手順](upgrade.md) に従い、管理画面の分離と監視タイマーの準備を完了してください。導入・更新コマンドはそちらへ集約しています。

管理画面へログインし直し、agentの稼働と「運用状況」の最終確認時刻を確認します。外部サービスが未設定でも、ローカルのバックアップや差分確認は利用できます。

標準のTLSは共通のCloudflare Origin CA証明書です。サイト別TLSの選択・更新は [v2ガイドのサイト別TLS](pjas-cert.md#サイト別tls) を参照してください。

## GitHub Appを接続する

1. 「接続設定と初回準備」で、管理画面のHTTPS URLを保存します。
2. 「GitHub Appの作成へ進む」からGitHubへ移動し、作成を確認します。App ID・秘密鍵・Webhookの合言葉は戻ってきた際に自動保存します。
3. 「リポジトリを許可する」を開き、使用するリポジトリだけを選びます。
4. 接続確認欄に `所有者/リポジトリ名` を入力し、「Appで読み取れるか確認する」を押します。
5. サイト登録で「GitHub」→「GitHub App（非公開にも対応）」を選びます。`.pjas`の読み込みにも同じ認証を使用します。

既存のGitHub Appも、詳細欄からApp ID・公開名・PEM秘密鍵を登録できます。必要権限はRepository permissionsの **Contents: Read-only / Metadata: Read-only** です。自動公開を使う場合はPushイベント、Webhook URL `https://管理画面のアドレス/hooks/github`、共通のWebhookの合言葉を設定してください。

秘密鍵とWebhookの合言葉はrootだけが読める `/var/lib/pjas-control` に保存します。取得のたびに対象リポジトリの読み取り用Installation tokenを発行し、Gitに渡す一時ファイルは終了時に削除します。個人用トークンや長期トークンをリポジトリURLへ埋め込む必要はありません。

管理画面をVPN・IP制限で保護している場合も、GitHubから届く `/hooks/github` だけは到達可能にします。初回準備コマンドは、このパスだけに例外を追加します。Cloudflare AccessやWAFを別途使っている場合は、そちらにも同じパスの例外が必要です。署名の合わない通知は受け付けません。

既存サイトの取得元・Public/Appの切り替えは、各サイトの「自動処理・予約」から行います。

## 安全に公開・予約する

「新しいバージョンを公開」でGitHubまたは圧縮ファイルを選ぶと、最初はファイルを取得して変更点を準備します。本番はまだ変更しません。作業画面の「変更点を確認して次へ進む」から、追加・変更・削除とファイルごとのGit差分を確認します。DB、`.env`、引き継ぐ共有データはコード差分へ出しません。

確認後は「今すぐ」または「日時を指定して予約」を選びます。予約は日本時間で1分後から30日以内です。予約日時には確認済みのファイルを使います。確認後に本番コード・公開中の版・サイト設定が変わった場合は、予約を失敗にして再確認を求めます。準備済みのファイルは32日間保存し、期限切れのものは自動削除します。

ビルド・公開後の準備処理が生成する成果物は、取得時点の差分には含まれません。DBの構造を変更する処理がある場合は、コードを戻してもDBの構造は戻りません。警告を確認し、必要なら試験公開で先に検証してください。

自動公開は、サイトの「自動処理・予約」で有効にしてブランチを指定します。Webhookの署名とコミット番号を確認し、ブランチの最新版ではなく通知されたコミットを取得します。同じ配信やコミットの再送は二重公開しません。予約した利用者の権限は、実行直前にも確認します。開始状態を確認できなくなった予約を勝手に再実行することはありません。作業履歴を確認してから予約を作り直してください。

## バックアップと復元

公開・コードの切り戻し直前に、共有データとファイル型DBを自動保存します。手動保存、定期保存、最低保存数・保存日数の指定にも対応します。保存数と日数の両方を超えたものだけを自動削除します。バックアップはストリーミングAES-256-GCMで暗号化し、途中欠落や改変も確認します。

SQLiteはSQLiteのバックアップAPIでコピーするため、稼働中のWALを含む内容を整合性のある形で取得します。一般の共有ファイルは順にコピーします。複数ファイル間の一括整合性が必要なアプリは、書き込みを停止して保存してください。MySQL・PostgreSQLなど外部のDBサーバーはこの対象に含まれません。

データ復元は管理者のみ操作できます。先にサイトを一時停止し、常駐プログラム・定期処理などの書き込みも止めてから確認欄にチェックします。復元直前にも安全用バックアップを保存します。復元中の公開再開を防ぐため設定操作をロックし、共有データを入れ替えます。成功してもサイトの停止状態は維持するので、内容を確認してから再開してください。

「暗号化ファイルを保存」で別の保管場所へダウンロードできます。「別サーバーで復旧するための暗号鍵を保管する」から、現在のパスワードを入力して暗号鍵も保管してください。鍵と暗号化ファイルは別の安全な場所へ保存します。鍵を紛失すると復号できません。

別のサーバーで中身を取り出す例です。

```bash
php8.5 bin/pjas-decrypt-backup demo-保存番号.pjas pjas-backup-key.txt restored.tar.gz
mkdir recovered
# 空の復旧用フォルダに取り出す。本番への上書きは内容を確認してから行う。
tar -xzf restored.tar.gz -C recovered
```

このバックアップはサイトの共有データ用です。管理画面のDB・二段階認証用鍵・GitHub Appの設定・Apache履歴を含むサーバー全体の復旧用には、`/var/lib/pjas`、`/var/lib/pjas-control`、`/var/lib/pjas-repositories`、`/var/lib/pjas-daemons`、`/var/lib/pjas-pauses`、`/etc/apache2`、`config.php` なども別途退避してください。

## 試験用URLを作る

「接続設定」で試験用の親ドメインを指定し、DNSをこのサーバーへ向けます。`example.com` を指定した場合、`preview-サイト名.example.com` を使います。CloudflareのプロキシとFull (strict)を使う場合は、親ドメインのワイルドカードが共通証明書に含まれていることを確認してください。Cloudflare Origin CA証明書はブラウザーから直接アクセスした場合には信頼されません。

サイトの「試験公開」で、**本番の接続情報を含まない試験用.env** を最初に保存します。次に、公開前の確認まで進めたバージョンを選択して試験URLを作成します。「試験URLのログイン情報を発行し直す」でID・パスワードを受け取り、開いて確認してください。パスワードはハッシュ保存し、再表示しません。

試験環境は専用ユーザー、専用PHP-FPM、systemdのPrivateNetwork、書き込み先制限で動かします。本番のDB・共有データは独立したコピー、本番の.envはコピー対象外です。外部DB・メールなどへのネットワーク接続、プロセス実行、標準のDB Unix socketへのアクセスを制限します。機密データを含む本番DBのコピーなので、試験URLのパスワードも安全に扱ってください。

試験公開はPHP・静的なビルド済みコード用です。独自のProxyPass・WebSocket・本番の準備処理は実行しません。外部DBや独自常駐サーバーが必須のアプリは、この試験環境の対象外です。通常のv1サイト同士は共通ユーザー（既定www-data）で動くため、相互に信用しない利用者向けの完全な実行環境分離を提供するものではありません。

## 利用者とログインの保護

管理者は「利用者とサイトの権限」で、利用者の追加・パスワード変更・停止、全サイトまたは指定サイトの閲覧・操作を設定できます。管理者は全サイトを操作できます。閲覧者にサイト単位の操作権限を指定しても、全体権限を超える操作はできません。最後の有効な管理者は停止・降格できません。

既存利用者のアクセス範囲は維持します。範囲を狭める場合は、対象利用者を編集してサイトを指定してください。サイト一覧、作業履歴、ログ、監査記録、公開・切り戻しのサーバー側の処理でも権限を確認します。

二段階認証は「ログインの保護」で各自設定します。認証アプリでQRコードを読み取り、6桁のコードで確認してから有効にします。QRコードはサーバー外へ送らずブラウザー内で生成します。復旧コードは各1回限りで、発行したときだけ表示します。設定時に安全な場所へ保存してください。同じTOTPコードのログインへの再使用、過剰な認証試行は拒否します。

## 通知・ログ・証明書

通知方法は「画面だけ」「Webhook」「メール」から選べます。メールはTLS/STARTTLSとサーバー証明書の確認を使用します。保存後のテスト送信で接続を確認してください。Webhookは `text` を含むJSONをHTTPSで送信します。

運用状況にはサイトの応答、起動を期待する常駐プログラムの異常、空き容量不足、証明書の期限・対象不一致、作業の失敗を表示します。障害の継続中は同じ通知を繰り返さず、復旧時にお知らせします。期限は残り30日未満、容量は10%または1GB未満を目安にします。証明書の確認は期限とドメインの一致で、CloudflareのDNS・WAF設定や信頼チェーン全体の検証を行うものではありません。

ログ画面は対象サイトに結び付いたApache・アプリの共有logs・公開作業・常駐プログラム・定期処理だけを扱います。一般的なパスワードや認証ヘッダーの表記を伏せますが、独自形式の秘密情報まですべて判別できるわけではありません。ログを必要以上に共有しないでください。

Apache設定の復元はGit履歴から選び、差分を確認してから実行します。確認後の設定変更は競合として止め、configtestや反映に失敗した場合は復元前の設定へ戻します。通常のエラーページ部分更新と、履歴からの全体復元は別の操作です。

## 検証

`tests/` の既存回帰テストに加え、GitHub AppのJWT・権限・一時認証情報の削除・Webhook署名、暗号化バックアップとSQLite復元、サイト権限・TOTP・復旧コード、公開前の差分・改変検知・コミット固定、予約/通知の重複防止、Apache復元の失敗時巻き戻し、試験DBの独立性を検証しています。

ブラウザー検証では、デスクトップ・スマートフォンでの画面表示、二段階認証の設定と復旧コードログイン、日時指定公開、権限外の画面の403応答を確認します。GitHub App実接続、実メール配信、Ubuntuのsystemdによる起動は、ご自身の認証情報・DNS・サーバー上で上記の初回準備と接続テストを行ってください。
