# セキュリティ確認と修正（2026-11-03）

[ドキュメント一覧](README.md) / [現在の更新手順](upgrade.md)

この文書は記載日の検証記録です。現在の導入・更新手順は上のリンクを参照してください。

## 結論と対象範囲

pjas-ctrlの認証、権限確認、特権RPC、ファイル操作、アーカイブ展開、GitHub/.pjas取り込み、Apache生成・復元、バックアップ、ログ表示をコードとテストで確認しました。改善が必要な問題を修正しています。**脆弱性が存在しないことや、過去に漏洩がなかったことを証明したものではありません。**

本番サーバーのOS・パッケージ・Apacheの実設定、アクセスログ、Cloudflare/WAF、各ホスト済みアプリのコードは確認していません。実際の漏洩の有無も判断できません。

## 修正した問題

| 重要度 | 問題・成立条件 | 対策 |
| --- | --- | --- |
| 高 | セッションが取得された場合、パスワード変更後も既存の認証状態を利用できた | パスワード・二段階認証・認証バージョンにセッションを結び付け、変更時に失効。利用者設定の更新でも認証バージョンを更新 |
| 高 | 特権RPCの共有ファイル書き込みで、予測可能な一時ファイルへのリンクから別ファイルを上書きできる処理だった | ランダムな排他的作成と、Web実行ユーザーへの権限降格を使用。入力は専用FDで渡し、秘密の本文をコマンド引数に載せない |
| 高 | rootでサイト所有ファイルを読み取る処理や、管理フォルダのリンク追跡に改善が必要だった | バックアップ・共有ファイル・アプリログをWebユーザーの権限で読み取り、管理フォルダのリンクを拒否。サイト直下・releasesの親をroot所有に保護 |
| 高・構成依存 | 公開フォルダ内に.env・ファイル型DB・秘密鍵・ログ・バックアップ・Git情報がある場合、直接配信を防ぐ共通設定がなかった | 共通Apacheポリシーを各VirtualHostの末尾で読み込む。通常のLocation許可による上書きも考慮し、新規生成・履歴復元・削除サイト復元時にも保護を維持 |
| 高・信頼する設定に依存 | リポジトリのconfに、外部プログラム・SSLエンジン・管理情報へのログ出力や、管理画面を置き換える名前を指定する余地があった | 危険な指示とログ出力先を制限。管理画面のServerNameに一致する公開名・ワイルドカード別名を拒否 |
| 対策強化 | アーカイブは展開後の検査が中心だった | root専用領域にハッシュ確認済みのコピーを作り、展開時に通常ファイル・ディレクトリのみ許可。リンク、特殊ファイル、絶対パス、親ディレクトリ参照、重複を拒否。10万件・4GBの上限 |
| 対策強化 | 二段階認証の設定変更、復旧コード、エラー表示・認証試行に改善の余地があった | 設定変更で現在のパスワードを必須化。新しい復旧コードを128bit化。機密値を含む認証情報は表示しない。PHPエラーを画面に表示しない。入力長とIP単位の制限を先に確認 |

特権RPCを直接使えるのは管理画面用の専用アカウントです。上記のファイル操作の問題について、公開サイトの匿名利用者がそのままRPCを呼べることを確認したわけではありません。危険なリンクを用意できることと、該当する管理操作が行われることが成立条件になります。

## 残る重要なリスク

- **サイト間の完全な隔離は未対応です。** 本番サイトのPHP・常駐プログラム等が同じwww-dataで動く構成では、1サイトのコード実行権限を奪われると、他サイトの同ユーザーのファイルへ影響する余地があります。ctrl画面のサイト別権限だけで、このOS権限の共有は防げません。個人情報を扱うサイトや信頼しない利用者を収容する場合は、サイトごとの実行ユーザー・PHP-FPM・データ権限の分離を次の優先対応にしてください。
- .pjas・フック・常駐プログラム・未知のApache設定は、実行コードとして信頼できるものだけを使用してください。危険な既知の指示を拒否しても、将来のApache追加モジュールを含む全指示の安全性を検証するものではありません。ローカルの既存confの継承は、管理者が信頼する設定であることが前提です。
- HTTPの共通保護は既知の拡張子・ファイル名による直接配信の対策です。拡張子のないDB、アプリ自身が返す個人情報、独自のAliasやプロキシ先、アプリ内の認証不備まで自動的に保護しません。DocumentRootをpublic等へ限定し、DB・共有データを公開範囲から外してください。
- ログの一般的な秘密情報は伏せますが、独自形式の個人情報を完全に判別できません。ログ閲覧権限を必要な利用者だけに付与してください。
- 実サーバーのセキュリティ更新・依存ライブラリの最新CVE照合・侵害履歴の調査は未実施です。

## 検証

- PHP回帰テスト38本（通常37本＋HTTP通信を使う停止・再開テスト）。
- Pythonのアーカイブ攻撃入力テスト8件。通常展開、親参照、絶対パス、シンボリックリンク、ハードリンク、特殊ファイル、ZIPリンク、重複エントリを確認。
- 再起動前の作業で、実HTTPによる複数セッションのパスワード変更時失効、二段階認証の有効化・解除時の本人セッション維持と他セッションの失効を確認。
- 再起動前の作業で、Apacheを実際に起動し、通常ファイルと.well-knownは200、.env・DB・秘密鍵・SQL・ログ・Git管理情報は403になることを確認。VirtualHostのLocation許可がある場合も確認。
- 本番環境へのインストーラ適用や、実際の顧客データによる攻撃再現は行っていません。

## 更新と運用上の変更

公開・削除などの作業が実行中でないときに更新してください。Python 3の標準ライブラリを使います。

```bash
cd /opt/pjas-ctrl
sudo git pull --ff-only origin main
sudo apt install -y python3
sudo -u pjas-control php8.4 bin/pjas-migrate
sudo php8.4 bin/pjas-install-features --check
sudo php8.4 bin/pjas-install-features --apply
```

`--apply`がApache保護設定・ディレクトリ権限を反映し、サービスを再起動します。**git pullと再起動だけでは共通の公開防止設定は有効になりません。** 管理画面のApache設定名が違う場合は、従来どおり`--site=設定名`を付けます。設定とDBの退避先はコマンドが表示します。

更新後はログインし直してください。二段階認証の設定変更には現在のパスワードが必要です。既存の復旧コードも引き続き使用できますが、「ログインの保護」から新しいコードを発行して保管してください。

圧縮ファイル内のリンクは拒否するようになります。必要な共有リンクはctrl側の共有設定で作成してください。DB・SQL・ログ・鍵等の拡張子を使う直接URLも403になります。意図的なファイル配信が必要な場合は、認証済みのアプリのダウンロード処理を利用し、公開設定を確認してください。
