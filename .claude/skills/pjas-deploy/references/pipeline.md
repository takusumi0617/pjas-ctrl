# デプロイの実行順序と、失敗したときに何が起きるか

`agent/ops/Deploy.php` の `run()` が実際に行う処理。どの段階で落ちたかが分かると、
本番が今どうなっているか（無事か、切り替わったか）を即断できる。

| # | 処理 | 失敗したときの状態 |
|---|---|---|
| 0 | **初回のみ** 既存ファイルを `releases/<tag-1s>` へ引き継ぎ、`current` をそこへ張る (単独で実行する `pjasctl adopt` も同じ処理。`references/migration.md`) | 引き継ぎ前に落ちれば既存ファイルはそのまま。引き継ぎ後は管理下のパスで既存サイトが配信される |
| 0 | メンテナンスページ ON (Web UI でこのオプションを選んだときのみ。`shared/maintenance.on` を作成。CLI にこのフラグは無い) | — |
| 1-3 | アーカイブの検疫と `releases/<tag>` への展開 (サイズ・拡張子・SHA-256・パストラバーサル検査) | **本番は無傷**。展開済みディレクトリは自動削除される |
| 4 | `shared_paths` のシンボリックリンク作成 | 同上 |
| 5 | 所有者・パーミッションの正規化 | 同上 |
| 6 | `after_deploy` フックを web ユーザーとして新リリース内で実行 | **本番は無傷**。フックは許可リスト内のみ実行される |
| 7 | `php -l` による構文検査、docroot の存在確認、`apachectl configtest` | **本番は無傷**。Apache は元の設定のまま動き続ける |
| 8 | `current` シンボリックリンクを新リリースへ張り替え、php-fpm reload / apache graceful | ここから先は新リリースが公開されている |
| 9 | ヘルスチェック (設定した URL と期待ステータスをポーリング) | 自動ロールバックが有効なら直前リリースへ戻して失敗終了。無効なら**新リリースが公開されたまま失敗終了** |
| 10 | `keep_releases` を超えた古いリリースを削除 | — |

読み取れる重要な性質:

- **8 の手前で落ちた失敗は、本番に影響しない。** 「デプロイが失敗した」と報告を受けたら、
  まずジョブログで 8 に到達しているかを見る。到達していなければサイトは前のまま動いている。
- **9 で自動ロールバックが働いた場合、サイトは前のバージョンに戻っている。** 直したうえで
  再デプロイすればよい。この状態でさらに手動 rollback を打つ必要はない。
- `--no-rollback` を付けた場合だけ、壊れた新リリースが公開されたまま残る。この状態を
  検出したら、原因調査より先に `rollback` で戻すこと。
- **初回デプロイでも自動ロールバックは効く。** 既存ファイルの引き継ぎで切り戻し先が
  作られるため。既存ファイルが無い（本当に新規の）サイトだけは切り戻し先が無い。

## リリース tag

`YYYYmmdd-HHiiss` 形式（例 `20260819-101204`）。デプロイ時刻そのもの。
`rollback` に渡すのはこの tag で、`--label` で付けた表示名ではない。
tag は `pjasctl services` の現行リリース欄、または Web UI の「バージョン履歴」タブで確認できる。
